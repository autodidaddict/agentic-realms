# Contract: Wipe-and-Replay Migration

Per FR-021a (clarified 2026-05-23 — Q2 Option A). The migration drops `world_npcs`, creates `npc_blueprints` + `npc_clones`, and resets the `WorldProjector` subscription. The projector replays the event store on next application startup.

## Migration file

`priv/repo/migrations/2026MMDDHHMMSS_introduce_npc_blueprints.exs`

```elixir
defmodule AgenticRealms.Repo.Migrations.IntroduceNpcBlueprints do
  use Ecto.Migration

  def change do
    # Drop feature 007's table. The data is recoverable from the event
    # store via WorldProjector replay (see subscription reset below).
    drop_if_exists table(:world_npcs)

    create table(:npc_blueprints, primary_key: false) do
      add :id, :string, primary_key: true
      add :name, :string, null: false
      add :short_description, :string, null: false
      add :long_description, :text, null: false
      add :is_synthetic, :boolean, null: false, default: false

      timestamps(type: :utc_datetime)
    end

    create table(:npc_clones, primary_key: false) do
      add :id, :binary_id, primary_key: true

      add :blueprint_id,
          references(:npc_blueprints,
            type: :string,
            on_delete: :restrict
          ),
          null: false

      add :serial, :integer, null: false
      add :name, :string, null: false
      add :short_description, :string, null: false
      add :long_description, :text, null: false

      add :room_id,
          references(:world_rooms,
            type: :binary_id,
            on_delete: :restrict
          ),
          null: false

      timestamps(type: :utc_datetime)
    end

    create index(:npc_clones, [:room_id])
    create index(:npc_clones, [:blueprint_id])
    create unique_index(:npc_clones, [:blueprint_id, :serial])

    create unique_index(
             :npc_clones,
             ["room_id", "LOWER(name)"],
             name: :npc_clones_room_id_lower_name_index
           )

    # FR-021a: Wipe-and-replay subscription reset. Deletes the
    # WorldProjector's tracking row so the next application startup
    # re-subscribes from event position 0 and rebuilds the entire read
    # model. Other projector handlers (rooms, exits, objects, player_state)
    # are idempotent via on_conflict: :nothing, so re-projection is safe.
    execute(
      """
      DELETE FROM subscriptions
      WHERE subscription_name = 'AgenticRealms.World.Projections.WorldProjector'
      """,
      ""
    )
  end
end
```

## Migration ordering

The migration runs as the next migration after the most recent existing migration (`20260523184435_create_world_npcs.exs` from feature 007).

The Ecto timestamp prefix for this migration will be later than the feature 007 migration — generated by `mix ecto.gen.migration` at implementation time.

## Application-startup behavior after migration

1. Migration ran: `world_npcs` dropped, `npc_blueprints` + `npc_clones` created (empty), `WorldProjector` subscription deleted.
2. Application starts. Commanded sees no subscription row for `WorldProjector`, so it starts from event position 0.
3. Projector replays the event store:
   - `RoomCreated` events → upsert into `world_rooms` (existing rows match by PK, `on_conflict: :nothing` no-ops).
   - `ExitAdded` events → upsert into `world_exits` (idempotent).
   - `ObjectPlacedInRoom` / `ObjectTakenFromRoom` / `ObjectDroppedInRoom` events → upsert into `world_objects` (idempotent).
   - `PlayerSpawned` / `PlayerMoved` events → upsert into `player_state` (idempotent).
   - `NPCSpawnedInRoom` events (feature 007 legacy) → synthetic blueprint + clone insert via the rewritten handler.
   - `NPCBlueprintCreated` + `NPCClonedFromBlueprint` events (if any exist from a prior 008 run, e.g., a test that already populated them) → upsert into new tables.
4. Projector subscription catches up to the current event-store position.
5. Application is ready.

Total replay time for the starter map (3 rooms, 3 objects, 1 NPC + however many player movements have happened in dev): under 1 second on a developer laptop.

## What about existing read-model data?

The migration ONLY drops `world_npcs`. It does NOT drop `world_rooms`, `world_exits`, `world_objects`, or `player_state`. Those tables retain their data; the projector's replay produces idempotent upserts that match existing rows.

This is the right tradeoff: only the NPC schema is changing, so only the NPC table needs to be rebuilt. Other tables would get the same data re-projected if they were dropped, but the unnecessary rebuild cost (and operational risk) is avoided.

## Verification (Story 5 / SC-005)

After a developer runs `mix ecto.reset` (which re-runs all migrations including this one and then runs `Seed.run/0`), the world's read model is observable as:

- `world_rooms`: 3 rows (Atrium, Corridor, Library)
- `world_exits`: 4 rows (paired N/S and E/W)
- `world_objects`: 3 rows (brass lantern, leather-bound journal, reading lectern)
- `npc_blueprints`: 1 row (`id: "garrick_the_innkeeper"`, `is_synthetic: false`)
- `npc_clones`: 1 row (`blueprint_id: "garrick_the_innkeeper"`, `serial: 1`)
- `player_state`: 0 rows (no players spawned yet on a fresh reset)

A test that asserts this end-state after `Seed.run/0` is the integration check for the migration's correctness.

## Edge case: rollback

`mix ecto.rollback` reverses the migration: drops `npc_clones` + `npc_blueprints`, recreates `world_npcs` with feature 007's schema. **However**, the rollback does NOT re-populate `world_npcs` — the data must be rebuilt by separately resetting the projector subscription (or running `mix ecto.reset` to reseed).

This is documented as expected behavior; rolling back a wipe-and-replay migration in production is unusual and should be paired with operational care.
